- Todas as rotas sob `routes/api.php`, `prefix('v1')`. Grupo autenticado sob `middleware(['jwt'])`.
- Endpoints existentes: `auth/login`, `auth/refresh`, `auth/logout`, `auth/my-tenants`, `auth/switch-tenant`, `users`, `groups` (+ `/users/sync`, `/permissions/sync`), `functionalities`, `tenants`, `tenant-roles` (+ `/permissions`), `tenant-users`, `client-categories`, `product-categories`, `product-types`, `estados`, `cidades`, `bairros` (globais, sem `tenant_id`), `enderecos`, `dias-ideais`, `periodos-ideais`, `clients` (+ `/categories/sync`), `products` — todos sob `tenant-roles`/`tenant-users`/`client-categories`/`product-categories`/`product-types`/`enderecos`/`dias-ideais`/`periodos-ideais`/`clients`/`products` exigem middleware `tenant`; `estados`/`cidades`/`bairros` são globais e não levam `tenant`. `products` é o único endpoint com upload de arquivo (`image`, multipart/form-data no mesmo `POST`/`PUT`, disco local via `Storage::disk('public')`).
- FK cross-tabela em Request (ex.: `ProductType.product_category_uuid`): usar `Rule::exists('table','uuid')->where(fn($q)=>$q->where('tenant_id', app('tenant_id'))->whereNull('deleted_at'))` — dá 422 (`VALIDATION_ERROR`) em vez de 404/500 quando a referência não existe ou é de outro tenant. Padrão introduzido em `ProductType` (2026-07-06), reaproveitável em qualquer FK tenant-scoped futura.
- **Toda Service de recurso tenant-scoped deve validar posse do tenant em `update()`/`delete()`** antes de qualquer outra coisa: `if ((int) $model->tenant_id !== (int) app('tenant_id')) { abort(404); }`. Route-model-binding (`HasUuid::resolveRouteBinding`) resolve só por `uuid`, sem filtrar tenant — sem esse guard existe IDOR (achado e corrigido em `ClientCategory`/`ProductCategory`/`ProductType`/`TenantRole` em 2026-07-06, ver [[architecture-decisions]]). Não depender só do `perm:` middleware, que valida a permissão, não a posse do registro.
- **Nunca usar `catch (\RuntimeException $e)` genérico num Controller** — `abort()`/exceções HTTP do Symfony (incluindo o 404 do guard acima) também estendem `\RuntimeException`. Para sinalizar regra de negócio (nome/slug duplicado etc.), usar uma exceção dedicada (`App\Exceptions\DuplicateNameException`, `App\Exceptions\LocationChainException`) e capturar essa classe especificamente.
- **FK opcional em update parcial**: só resolver/validar a entidade referenciada quando o campo correspondente vier no DTO (`if ($dto->xUuid) { ... }`) — nunca usar `findOrFail()` como fallback pro valor já salvo quando o campo não veio no request. `findOrFail` respeita soft-delete; se a entidade referenciada por um campo *não tocado* pelo update tiver sido soft-deletada depois, isso quebra um update legítimo com 404 enganoso (achado em `EnderecoService::update`, 2026-07-06 — ver [[architecture-decisions]]). Quando for necessário resolver o valor já salvo (porque outro campo da mesma cadeia está mudando), usar `withTrashed()->findOrFail()` no fallback, não `findOrFail()` puro.
- **Filtro boolean de query string nunca usa `empty()`**: `empty('0')` e `empty(false)` são `true` em PHP, então `if (!empty($filters['x']))` ignora silenciosamente o valor `"0"`/`false` vindo da query string (`?is_trusted=0` vira "sem filtro" em vez de "filtra por false"). Usar sempre `array_key_exists($filters, 'x') && $filters['x'] !== null` (achado em `ClientService::paginate`, 2026-07-08 — ver [[architecture-decisions]]).
- **`ModelNotFoundException` vira 404 automaticamente** (conversão padrão do Laravel para `NotFoundHttpException`, antes da cadeia de `render()` customizada em `bootstrap/app.php`) — não é preciso (nem deve) registrar handler específico para isso, já cai no `render(NotFoundHttpException ...)` existente.
- Resposta sucesso: `{ success: true, message, data, meta: { request_id, ...pagination? } }`.
- Resposta erro: `{ success: false, message, code, errors, meta }`.
- Paginação: `per_page` via query (default 15), `meta.pagination` com `current_page/per_page/total/last_page`.
- Toda rota de mutação exige `perm:{functionality_slug},{action_key}`; 403 retorna `code: FORBIDDEN`.
- Header `X-Request-Id` propagado em `meta.request_id` de toda resposta de sucesso.
- **Contrato genérico de sort/filter para grids server-side (ag-Grid Infinite Row Model)**, introduzido em `Client`/`Product`/`ProductCategory`/`ProductType` (2026-07-09), reaproveitável em qualquer novo grid: query params `sort_by` (string) e `sort_dir` (`asc`|`desc`, default `asc`) validados por `FormRequest` dedicado (`Http/Requests/{Feature}/List{Feature}Request.php`, com `page`, `per_page` min:1/max:100, e os filtros do recurso). Controller passa `$request->validated()` direto pro Service (sem `$request->only()` cru). Service mantém `private const SORTABLE = ['nome_publico' => 'tabela.coluna_sql']` — whitelist interna, nunca interpola `sort_by` direto na query; `sort_by` ausente/fora da whitelist cai no fallback de ordenação antigo do recurso (não quebra comportamento pré-existente). Filtro "contains" em coluna de relação (ex.: `cidade_name`, `product_type_name`, `product_category_name`) e ordenação pela mesma coluna exigem `leftJoin` explícito na tabela relacionada (só quando `sort_by` ou o filtro correspondente estão presentes, montado condicionalmente) + `select('tabela_principal.*')` sempre (evita "ambiguous column" quando a tabela joinada tem coluna com mesmo nome, ex. `name`). Seguro sem duplicar linhas só porque a relação é `belongsTo` 1:1 (endereco→cidade, product→product_type→product_category); não aplicar esse padrão a relações many-to-many/hasMany sem paginação por `DISTINCT`/`groupBy`. Filtro numérico em range usa par `{campo}_min`/`{campo}_max` (ex. `price_min`/`price_max`, `priority_min`/`priority_max`), com guarda `array_key_exists(...) && ... !== null && ... !== ''` (mesma cautela do padrão de boolean já registrado acima, `''` também precisa ser tratado como "sem filtro").
- **Busca global de grid (`q`)**, adicionada em cima do contrato de sort/filter acima (2026-07-09), mesmos 4 recursos: query param `q` (string, opcional, `max:255` na `List{Feature}Request`) faz OR-contains entre as colunas "buscáveis" do recurso — independente e cumulativo (AND) com os filtros por coluna já existentes, nunca os substitui. Colunas buscáveis por recurso: Client `name`/`phone_primary`/`cidade_name`; Product `name`/`product_type_name`/`product_category_name`; ProductCategory só `name`; ProductType `name`/`product_category_name`. Implementação na Service: um único `$query->where(function ($sub) use ($term) { $sub->where(...)->orWhere(...)->orWhereHas('relacao', fn($r) => $r->where('name', 'like', "%$term%")); })` — o agrupamento em closure é obrigatório pra o OR interno não vazar e virar OR com o tenant scoping/soft-delete/filtros por coluna de fora do grupo. Busca em coluna de relação usa `orWhereHas` (subquery correlacionada própria), não o `leftJoin` condicional do sort_by — não precisa do join presente pra funcionar, os dois mecanismos são independentes mesmo operando sobre a mesma relação.
- **Escopo do contrato genérico de sort/filter estendido a `Location` (Estado/Cidade/Bairro/Endereco)**, 2026-07-12 — mesmas regras acima (`sort_by`/`sort_dir`, `SORTABLE` whitelist, `leftJoin` condicional + `select('tabela.*')`, `_min`/`_max`/bool), sem `q` (não venda neste recurso). Particularidades: Estado é global (sem `tenant_id`, sem `assertBelongsToCurrentTenant`); Cidade (`sort_by ∈ {name, estado_name, is_active}`) e Bairro (`sort_by ∈ {name, cidade_name, is_active}`) preservam o filtro exato de cascade pré-existente (`estado_uuid` em Cidade, `cidade_uuid` em Bairro, via `whereHas`) usado pelos dropdowns em cascata do form de Cliente/Endereco — não remover nem renomear; convivem sem conflito com o `leftJoin` condicional porque operam em mecanismos distintos (`whereHas` vs `leftJoin`+`select`). Endereco (`sort_by ∈ {logradouro, cep, cidade_name, bairro_name, is_active}`, tenant-scoped) referencia `cidade_id`/`bairro_id` diretamente na própria tabela (não via cadeia indireta), então os dois `leftJoin` (`cidades`, `bairros`) são independentes entre si, cada um montado só quando o sort/filtro correspondente está presente.
- **Teste local de permissão (`grantPermission`) precisa sufixar `groups.name`, não só `groups.slug`**: `groups.name` também é `unique` no schema; um helper `grantPermission()` que hardcoda `'name' => 'RBAC Group'` (só variando o slug) quebra com `UniqueConstraintViolationException` assim que o mesmo teste chama `grantPermission()` mais de uma vez (ex.: `create` + `read` no mesmo teste para popular dados e depois listar). Achado em `Estado/Cidade/BairroPermissionsTest` (2026-07-12) — esses 3 arquivos tinham um `grantPermission` local (cópia independente do trait `SetsUpTenantScopedUser`) sem esse cuidado; corrigido pra sufixar `name` com o mesmo `$suffix` do `slug`, replicando o padrão já correto do trait. Ao copiar/colar esse helper local em teste novo, usar sempre o padrão do trait, não o hardcoded.
- **Gestão manual de parcela de Venda** (`POST`/`PUT`/`DELETE /sales/{order}/installments[/{installment}]`, 2026-07-12): contrato `{ installment_number: int, amount: decimal, due_date: date }` idêntico em create/update (substituição completa, não parcial); resposta usa `OrderInstallmentResource`, **mesmo shape exato** do array `installments[]` já embutido em `SaleResource` (`uuid`, `installment_number`, `amount`, `due_date`, `is_paid`, `paid_at`) — não criar um segundo formato pro mesmo dado. Protegido por `perm:sales,update` (create/edit) e `perm:sales,delete` (excluir) — `update`/`delete` já existiam como `Action` globais (usados por outros recursos) e `sales` já existia como `Functionality`; **nenhuma mudança de seeder foi necessária** (`AdminPermissionsSeeder` já concede o produto cartesiano de TODAS as functionalities × TODAS as actions ao grupo `administrators`, dinamicamente via query, não por lista hardcoded — qualquer par novo já reconhecido automaticamente). Controller/Service dedicados (`OrderInstallmentController`/`OrderInstallmentService`), não métodos extras em `OrderController`/`SaleService` — mesmo padrão já usado em `TenantRolePermissionController`/`TenantRolePermissionService` pra sub-recurso aninhado com regra de negócio própria.
- **`PUT /sales/{order}/installments` (lote, sem `{installment}` na URL — coexiste sem conflito de rota com o `PUT .../installments/{installment}` individual acima), 2026-07-12**: substitui de uma vez todas as parcelas NÃO PAGAS do venda. Body `{ installments: [{ uuid?: string, installment_number: int, amount: decimal, due_date: date }, ...] }` — item **sem** `uuid` cria parcela nova; item **com** `uuid` de parcela não paga existente atualiza; parcela não paga existente **ausente** do array é excluída (soft delete); `uuid` de parcela já paga no array é sempre rejeitado (422), nunca silenciosamente ignorado. Resposta: array completo de `OrderInstallmentResource` (parcelas pagas + as recém-processadas, ordenado por `installment_number`). Mesma proteção (`tenant`, `perm:sales,update`, dentro de `DB::transaction` com `lockForUpdate()` no `Order` + em TODAS as parcelas do venda). **Diferença estrutural chave**: a validação de soma (`amount` de todas as parcelas ativas == `sales.total_amount`, em centavos) roda **uma única vez, no final da operação inteira**, não a cada item — é isso que permite redistribuir valor entre parcelas numa chamada só (ver entrada correspondente em [[architecture-decisions]] sobre por que os 3 endpoints individuais não conseguem fazer isso). Se a validação final falhar, toda a operação é revertida (nenhuma parcela muda) — mesmo padrão "tudo ou nada" via exceção propagando de dentro do `DB::transaction`.
- **`PUT /sales/{order}/items` (edição de itens/cabeçalho de venda já criado), 2026-07-14** — `SaleService::updateItems()`, estruturalmente análogo a `OrderInstallmentService::reallocate()` (diff do array inteiro contra o estado atual via `uuid`: item com uuid existente atualiza, sem uuid cria, item atual ausente do payload é removido), com a diferença de que cada item também mexe em reserva de estoque (`StockService::reserve`/`reserveCancel`, mesmo padrão de `create()`). Escopo deliberadamente limitado: não edita `client_uuid`/`is_installment` (decisão estrutural demais — cancela e recria se errado); só permitido enquanto `!is_delivered && !is_paid && cancelled_at===null` (`assertSaleItemsEditable`, reaproveita as mensagens `already_delivered`/`already_paid`/`already_cancelled` já existentes, 422 `INVALID_ORDER_STATE`). Reaproveita `perm:sales,update` (mesma permissão já usada na gestão manual de parcela) — nenhuma Functionality/Action nova. Update de item existente só toca estoque quando produto OU quantidade mudam (`reserveCancel` da reserva antiga + `reserve` nova); troca só de `unit_price` atualiza o valor sem gerar movimento de estoque ruído. Resolução de preço de item novo/trocado sem `unit_price` explícito no payload segue a mesma regra de `create()` (`ProductPricingService::resolvePrice`); item existente sem mudança de produto e sem `unit_price` no payload preserva o preço já gravado (não repreça silenciosamente um item intocado mesmo que `Product.price` tenha mudado desde a criação). `total_amount` sempre recalculado como soma de `line_total` dos itens vivos ao final; venda parcelado tem o total mudado mas as installments NÃO são recalculadas automaticamente (intencional — usuário ajusta depois via `PUT /sales/{order}/installments`). Validação "tudo ou nada" idêntica a `reallocate()`: uuid duplicado no payload ou uuid que não pertence ao venda → 422 `INVALID_ORDER_STATE` antes de qualquer mutação. Evento `SaleItemsUpdated` + listener `AuditSaleItemsUpdated` (mesmo padrão simples de `OrderUndelivered`). Sem migration nova (só usa colunas/tabelas já existentes de `sales`/`sale_items`). Testes em `tests/Feature/Orders/OrderTest.php` (12 novos: add/remove/troca de quantidade/troca de produto/edição só de cabeçalho/3 estados bloqueados/uuid estranho ao venda/uuid duplicado/produto de outro tenant/venda parcelado sem tocar installments) — 473 testes passando no total.

- **`unique()` numa coluna de tabela com `SoftDeletes` NÃO filtra `deleted_at`**: a constraint única do banco (ex.: `uniq_order_installment_number` em `sale_installments`, `(sale_id, installment_number)`) continua valendo pra uma linha soft-deletada — o valor "ocupado" por uma linha excluída (`deleted_at` preenchido) não fica livre pra reuso até a linha ser fisicamente removida ou o valor da coluna única ser alterado. Isso é diferente do padrão já registrado de checagem de disponibilidade em nível de aplicação (`whereNull('deleted_at')` antes de inserir/atualizar, ver `assertInstallmentNumberAvailable` em `OrderInstallmentService`) — a checagem de app corretamente diz "disponível" (porque filtra soft-deleted), mas o INSERT/UPDATE real ainda colide na constraint do banco. Achado real via bug reportado pelo frontend (2026-07-12): excluir uma parcela e criar uma nova reaproveitando o mesmo `installment_number` na mesma operação (ou em chamadas HTTP separadas) dava 500 cru. **Padrão de correção**: antes de qualquer soft delete de uma linha cuja coluna única pode ser reaproveitada depois, mudar o valor da coluna pra um sentinela garantidamente único (ex.: `1_000_000 + $model->id`, usando a PK auto-increment — globalmente única — como base) e salvar, só then chamar `->delete()`. Reaproveitável em qualquer tabela futura que combine `SoftDeletes` + unique key "reciclável" (ex.: `slug`, número sequencial, código). Ver `OrderInstallmentService::releaseNumberAndDelete()`.
- **`lang/{locale}/validation.php` não existia no projeto até 2026-07-12** — toda `FormRequest` sem `messages()` customizado (a maioria delas, pra regras padrão tipo `required`/`date`/`numeric`/`min`/`prohibited_if`) sempre retornava a mensagem em inglês no campo `errors`, **independente do locale ativo** (`App::setLocale()` via `SetLocale` middleware funciona normalmente pra `__('messages.xxx')` custom, mas Laravel usa o arquivo `validation.php` — não `messages.php` — pras mensagens de regra padrão, e sem esse arquivo publicado cai no fallback interno do framework, sempre em inglês). Achado real via bug reportado pelo frontend (2026-07-12: "422 veio em inglês", inicialmente suspeitado como chave faltando em `messages.php`, mas as chaves custom já estavam 100% corretas nos dois locales — o problema era esse arquivo ausente). Corrigido publicando `lang/en/validation.php` e `lang/pt_BR/validation.php` (conjunto completo padrão do Laravel, tradução pt-BR oficial) — fix sistêmico, vale pra qualquer FormRequest do projeto, não só as de Order/parcela. Novo FormRequest não precisa de `messages()` próprio só pra cobrir regras padrão (`required`, `date`, `numeric`, etc.) — só pra mensagens de regra CUSTOM que reaproveitam uma chave de `messages.php` (padrão já usado, ex. `'mark_as_paid.prohibited_if' => __('messages.sale.mark_as_paid_requires_non_installment')` em `StoreOrderRequest`).

- **Analytics (Fase 1 do roadmap), 2026-07-12** — 8 endpoints `GET /reports/analytics/*`, tenant-scoped com `perm:analytics,read` (Functionality nova `analytics`, só nos planos professional/premium — tenant no basic recebe `403 PLAN_UPGRADE_REQUIRED` do `CheckPermission`; premium ganha automaticamente porque `InitialPlansSeeder` faz `pluck('slug')` de todas as functionalities em runtime, e `FunctionalitiesSeeder` roda antes). `AnalyticsController` + `AnalyticsService` dedicados (`app/Services/Report/AnalyticsService.php`), FormRequests em `Http/Requests/Report/Analytics*` (base `AnalyticsPeriodRequest`, `from`/`to` nullable date). Regras comuns: venda cancelado SEMPRE excluído; `from`/`to` opcionais com default últimos 12 meses (filtro por `sales.created_at`), exceto `sales-history` (histórico completo); agregação sempre via `groupBy`/`selectRaw` no SQL — funções de data resolvidas por driver (`strftime`/`julianday` no SQLite dos testes, `DATE_FORMAT`/`DATEDIFF`/`YEAR`/`MONTH` no MySQL) em métodos `*Expression()` privados; dinheiro como string `"123.00"`. Contratos: `sales-summary?group_by=day|month` → `{group_by, current: {from,to,total_sales,total_revenue,average_ticket,buckets:[{bucket,order_count,revenue,average_ticket}]}, previous: <mesmo shape, período anterior de mesma duração>}`; `top-products?limit=10` → `[{product_uuid,product_name,quantity_sold,revenue}]`; `sales-by-location` → `{by_city:[{uuid,name,order_count,revenue}], by_neighborhood:[...]}` desc por revenue; `sales-history` → `[{year, months:[{month:1..12,count,revenue}]}]` anos desc, meses zerados incluídos; `top-clients?limit=10` → `[{client_uuid,client_name,order_count,total_amount,last_order_at,rfm_label}]`, `rfm_label ∈ vip|recorrente|em_risco|inativo` por tercis R/F/M (regra documentada em `AnalyticsService::topClients`/`rfmLabel`; tercis sobre TODOS os clientes do período, não só o top N); `payment-delays?limit=10` → `[{client_uuid,client_name,avg_days_to_pay,order_count}]` (média `delivered_at`→`paid_at`, ambos não-null, `AVG(DATEDIFF)` no SQL) desc; `overdue-sales` (paginado `per_page`/`page`, único paginado do grupo) → `[{sale_uuid,client_name,type: pagamento|entrega,open_amount,days_overdue}]` desc por dias — `pagamento` agrega parcelas vencidas não pagas por venda (soma em aberto, maior atraso) ou venda não parcelado com `due_date` vencido não pago; `entrega` = `expected_delivery_date` estourado sem entrega (um venda pode gerar uma linha de cada tipo); `abc-analysis?dimension=products|clients` (default products) → `{dimension,total_revenue,items:[{uuid,name,revenue,participation_percentage,cumulative_percentage,curve_class}]}`, curva A ≤80% / B ≤95% / C resto do acumulado.

- **Convite de usuário novo por e-mail (`tenant_user_invites`), 2026-07-13** — resolve a lacuna de `TenantUserService::create` só vincular um `User` global já existente (exige `users:read`, reservado a admin). `POST /tenant-users/invite` (tenant-scoped, `perm:tenant_users,create` — reaproveitada, não criou Functionality/Action nova) `{name, email, role_uuid}` → cria `TenantUserInvite` (token aleatório `Str::random(64)`, só o hash `sha512` fica no banco — mesmo padrão de `RefreshToken`/`AuthService::createSession`, não `sha256` como uma sugestão inicial cogitava), envia `TenantUserInviteMail` (via `MAIL_MAILER` configurado no `.env`) com link `{FRONTEND_URL}/convite/{token}` (`config('app.frontend_url')`, nova env `FRONTEND_URL`, default `http://localhost:5173`). Bloqueia com `422 EMAIL_ALREADY_REGISTERED` se já existe `User` global com o e-mail (não linka silenciosamente) e `422 DUPLICATE_INVITE` se já existe convite pendente (não expirado, não aceito) pro mesmo e-mail na mesma tenant — essa checagem é em nível de aplicação, não unique composta no banco (não representável como unique parcial simples no MySQL, e precisa permitir reconvite após expiração/aceite). `POST /auth/accept-invite` (público, sem `jwt`/`tenant`, `throttle:10,1,accept-invite`) `{token, password, password_confirmation}` → valida hash+expiração+não-aceito (`422 INVALID_INVITE_TOKEN` cobre os 3 casos, mensagem varia), cria `User`, faz *bind manual* de `tenant_id`/`tenant_uuid` no container (`app()->instance(...)`, réplica do que `ResolveTenant` faria) antes de reaproveitar `TenantUserService::create()`, marca `accepted_at`, retorna sessão já logada via `AuthService::createSession` (mesmo padrão de `SelfSignupService::register`). **Bug achado via teste, corrigido**: `TenantUserService::create()` chamava `Auth::id()` direto pro `actorId` do evento `TenantUserCreated` — em contexto público (sem usuário autenticado ainda) isso é `null`, e o construtor do evento exige `int`, gerando `TypeError`/500. Corrigido com o mesmo padrão já usado em `TenantService::create()` (parâmetro opcional `?int $actorId = null`, fallback `Auth::id() ?? $user->id`); `AcceptTenantUserInviteService` passa `actorId: $user->id` explicitamente. `created_by`/`updated_by` do `TenantUser` criado nesse fluxo ficam `null` (via `BaseModel`/`AuthContext::safeUserId()`, que também depende de `Auth::id()`) — aceito de propósito, mesmo padrão já existente pro `User`/`Tenant` criados em `SelfSignupService` (não há "ator" autenticado ainda nesse momento, é auto-registro). Coluna `invited_by` sugerida inicialmente foi **descartada** — redundante com `created_by` (que `BaseModel` já preenche automaticamente com o autor do convite). Migration `create_tenant_user_invites_table` já rodada em produção.

- **Proteção do perfil "owner" contra alteração pelo dono da empresa, 2026-07-13** — o role auto-provisionado por `TenantProvisioningService::createOwnerRole()` (`slug='owner'`) é identificado só por slug (sem coluna dedicada `is_protected`; decisão deliberada, é assim que ele já é identificado no resto do sistema). `TenantRoleService::update()` e `TenantRolePermissionService::syncPermissions()` agora bloqueiam qualquer ator que não esteja no grupo global `administrators` (`PermissionService::userHasGroupSlug`) de alterar nome/slug/is_active ou sincronizar permissões do role `owner` — o dono da empresa (grupo `clients`), mesmo com `tenant_roles:update` de sempre, não pode mais enfraquecer o próprio perfil `owner`; criar/editar/sincronizar permissões de QUALQUER OUTRO role continua liberado sem mudança. `TenantRoleService::delete()` bloqueia exclusão do role `owner` **incondicionalmente, inclusive para admin da plataforma** (decisão: nenhum cenário legítimo justifica apagar o único role que sustenta o acesso do dono a uma tenant ativa). Exceção dedicada `App\Exceptions\ProtectedTenantRoleException` (mesmo padrão de `DuplicateNameException`), capturada nos 3 controllers (`TenantRoleController::update/destroy`, `TenantRolePermissionController::sync`) como `APIResponse::error(..., 403, 'PROTECTED_ROLE')`.
